# Производственный календарь: сменный режим и «По выходным и праздникам»

## Назначение документа

Этот документ фиксирует смысл производственного календаря для будильника
«По графику» и для режима «По выходным и праздникам» (`calendar`).

## Основное правило

В сменном режиме источником времени звонка всегда остаётся сменный цикл:

```text
утро — своё время;
день — своё время;
ночь — своё время накануне;
отдельный слот может быть без звонка.
```

Производственный календарь не создаёт новое фиксированное время и не заменяет
времена цикла.

## Что означает «Учитывать праздники»

Для сменного графика эта настройка означает:

```text
звонить по временам сменного цикла;
не звонить, если день обслуживаемой смены является
официальным нерабочим днём по производственному календарю.
```

Для ночной смены проверяется день самой смены, а не календарный день вечернего
звонка накануне.

## Почему в сменном режиме не было «По выходным»

Полярность REST была разработана как простой календарный будильник с одним
фиксированным временем:

```text
в официальный нерабочий день звонить в HH:MM;
в официальный рабочий день молчать.
```

Сменный график имеет несколько времён и собственную ротацию. Если применить
старую REST-ветку к смене, движок игнорировал цикл и использовал скрытые
`AlarmEntity.hour/minute`. В результате пользователь настраивал, например,
05:00 / 13:00 / 21:00, а фактический звонок мог быть в невидимые 07:00.

Поэтому «По выходным» никогда не показывалось для режима «По графику» (а с фазы D
переключатель полярности убран из UI вовсе — сценарий «будить в дни отдыха» стал
отдельным режимом «По выходным и праздникам»).

Если пользователю нужен отдельный сигнал в официальные выходные, для этого есть
отдельный режим «По выходным и праздникам» (см. ниже). Несколько независимых
будильников в одни сутки допустимы.

## «По выходным и праздникам» — отдельный режим (`calendar`)

«Звонить в официальные нерабочие дни» — собственное значение режима будильника:
`mode = calendar` (`AlarmEntity.MODE_CALENDAR`). Прежняя комбинация полей
«по дням недели + учитывать праздники + полярность REST» больше не поддерживается.
Пользовательское название — «По выходным и праздникам» (без слова «страна»):

    суббота и воскресенье — звонит;
    праздник и перенесённый выходной — звонит;
    рабочий день, включая перенесённую рабочую субботу — молчит.

Свойства режима (инварианты фазы D):

- производственный календарь учитывается **всегда** и не выключается: тумблер «Учитывать
  праздники» в этом режиме не показывается (D-1);
- маска дней недели в расчёте не участвует и не обнуляется в БД (D-2): при возврате
  в «По дням недели» отмеченные дни сохраняются;
- периоды без будильника (отпуск/больничный/…) глушат звонок, как в других режимах (D-4);
- при отсутствии данных календаря на год режим деградирует до Сб/Вс.

В weekly-режиме полярности больше нет: `polarity` — legacy-колонка, движок читает REST
только в режиме `calendar` и игнорирует поле в остальных режимах (D-5).

Запланированное изменение (фаза C, «рабочая неделя» как настройка): режим `calendar` начнёт
считать нерабочие дни от рабочей недели пользователя (для 6-дневки — только воскресенье
и праздники), а не от стандартной недели страны. Сейчас — до реализации C — используется
стандартная неделя страны (Пн–Пт).

## Совместимость со старыми данными

Старая сменная запись может содержать:

```text
mode = shift
polarity = REST
```

Такая запись не должна использовать скрытое общее время.

При чтении и расчёте она безопасно трактуется как:

```text
mode = shift
polarity = WORK
```

После повторного сохранения запись нормализуется в БД.

Схема таблицы не менялась (новых колонок нет), но с фазы D есть **data-миграция 6→7**
(Room `version = 7`, `AppDatabase.MIGRATION_6_7`): записи

```text
mode = weekly
honorHolidays = 1
polarity = REST
```

переносятся в `mode = calendar` — прежняя комбинация «по дням недели + учитывать
праздники + по выходным» стала режимом «По выходным и праздникам». Записи без
`honorHolidays` не переносятся: при выключенном тумблере REST не действовал, и запись
фактически была weekly-WORK. `daysMask` не обнуляется: в новом режиме она не участвует
в расчёте, но остаётся данными пользователя (D-2).

Даунгрейд не поддерживается: старая версия приложения прочтёт `mode = calendar` как
weekly (защитное чтение) и будет звонить по маске дней — см. `docs/RELEASE_CHECKLIST.md`.

## Согласованность интерфейса

Для сменного режима одинаковое правило используют:

```text
боевой AlarmTimes.next;
строка «Следующий звонок»;
мини-превью;
календарь смен;
сохранённая запись.
```

То есть UI больше не может показать времена смен, а системный планировщик —
поставить скрытое фиксированное время.

## Проверка тестами

Unit-тесты проверяют:

```text
сменный режим не поддерживает REST;
weekly не поддерживает REST: полярность legacy, расчёт вне calendar — всегда WORK;
режим calendar — всегда REST: звонит в нерабочие дни, молчит в рабочие;
calendar игнорирует выключенный тумблер «Учитывать праздники» (календарь всегда включён)
и не читает маску дней;
нет данных на год — calendar деградирует до Сб/Вс;
старая сменная запись нормализуется в WORK;
смена использует время цикла, а не hour/minute;
официальный праздник и выходные глушат старую REST-запись как WORK.
```

## Проверка на устройстве

В сменном режиме:

```text
переключателя полярности «По рабочим / По выходным» нет (убран из UI);
описание говорит, что официальные нерабочие дни глушат звонки графика;
предпросмотр сохраняет времена смен;
после сохранения и повторного открытия поведение не меняется.
```

## Правило для будущих изменений (реализовано в фазе D)

Когда-то было решено: если появится полноценный календарный способ расписания
«По официальным рабочим/выходным дням», его следует оформить отдельным
пользовательским способом, а не скрытой полярностью сменного цикла. Так и сделано:
режим `calendar` («По выходным и праздникам») — первоклассное значение `mode`,
а выбор полярности убран из UI.
